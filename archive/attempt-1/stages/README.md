One folder per stage, holding that stage's latest configuration: skill, pinned rubrics, prompts, the commands to apply and run it, the result, and a short **Findings** table (issue → what we did). The first climb (world v2) was removed from the workspace on 2026-10-08; its lessons are in [JOURNEY § 4](../docs/JOURNEY.md#4-what-we-carried-from-the-first-climb).

**World v3** (why it differs from v2): the claim system answers in **one call** (`get_claim_dossier`), with **records only**, so no tool tells the agent which source governs. Labour rates are in **one workbook**. A claim needs about 4–6 tool calls instead of 13–17; every trap is kept.

## Rules
1. **One change per stage**, compared with the stage before. Say plainly if two things must move together.
2. **Report three numbers:** the platform's rubric score, ground-truth correctness (`scripts/score_ground_truth.py`), and the hand-in rejection rate.
3. **Rubrics are pinned files.** Samples capture the rubrics at upload, so re-upload samples when the rubrics change.
4. **Run claims in batches of 5 per evaluation job** ([scripts/eval-batches.ps1](../scripts/eval-batches.ps1)). Each job pays ~9 min of platform start-up, so one claim per job wastes most of the time. The runner heals platform stalls: a job with no progress for 15 min is cancelled, finished claims are kept, and unfinished ones are requeued (up to 3 attempts). Snapshot and reset the database after each job.
5. **A stage folder holds its latest configuration**; a superseded run is deleted (git keeps it), and the fix becomes one line in Findings.
6. **Tag each closed stage in git**: `v3-stage-0`, `v3-stage-1`, …
7. **Fail closed on infrastructure errors.** Runner CLI calls are bounded; SQL snapshot/reset errors stop subsequent jobs, and a clean baseline is checked before starting and after resetting. Cancellation is reconciled before reset, but late writes from in-flight executions remain a platform risk. Exhausted claims end the runner as incomplete, not “ALL DONE”.
